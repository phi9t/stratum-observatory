# Anchor residue decisions

Citations that no tool could anchor, and what was decided about each. Three resolutions are
allowed: **re-pointed** to a source that states the fact, **dropped** so `CLAIM_ROLE` reports the
gap honestly, or **reclassified** within the existing `PRESENTATION_SUFFIXES` whitelist. A row may
also stand as **unresolved** with a stated reason. Inventing a quote is not a resolution.

The unit of decision is the **class**, not the row. Writing three thousand rows one per line
produces a document nobody reads, and an unread table discards the same evidence a missing table
would -- only less visibly. Each row below is one `(source, reason, field-class)` group with its own
count, and the counts reconcile to the residue total exactly.
`verification/tests/test_anchor_tools.py` enforces both halves of that: every residue row falls
inside a recorded class, and no class may overstate or understate its own count.

This file is generated by `tools/anchor-residue.py` from the census reports under
`verification/reports/`. `anchor-residue-config.json` and `anchor-residue-documents.json` are the
population Tasks 2 and 3 judged, and are deliberately **not** regenerated: rerunning them against
today's bytes would renumber 2,987 decisions that were made against different ones.
DeepSeek-V4.1-Flash, added later, is censused separately in `anchor-residue-dsv41-config.json` and
`anchor-residue-dsv41-documents.json` -- the same two tools run with `--only dsv41`, so the ninth
checkpoint's rows are judged without disturbing the eight that came before.

Both censuses share one blind spot, stated here rather than left to be discovered: the two
authoring tools enumerate CONFIGURATION and DOCUMENTARY citations only. Citations of
`publisher_code` and `library_code` sources -- which are anchored by `python_symbol` selectors --
appear in neither report, so unanchored code citations are counted by `CLAIM_ANCHOR` in the
publication report but are not classified below. For the ninth checkpoint those are enumerated by
hand in the findings section that follows.

## Findings recorded individually

Six questions were put to this task by name. Each is answered here and each is carried by a class
in the table below, so the answer and the count cannot drift apart.

**1. `MODELS.q3827.linearGate`: the app shows `SiLU`, Qwen's configuration says `"swish"`.**
Same function, two names -- SiLU is Swish-1 (`x * sigmoid(x)`), and Qwen3.8 selects it through
`output_gate_type`. The anchor at `/text_config/output_gate_type` stands and is correct. Its
relation stays `documents` and was deliberately not upgraded to `equal`, because `equal` compares
the upstream bytes with the displayed value and `"swish"` is not `"SiLU"`. Upgrading it would make
the gate assert something false in order to look greener.

**2. The Qwen3 report states a 151,669-token vocabulary; the app shows 151,936.**
Both numbers are right and they measure different things. The report's sentence is about the
tokenizer -- "Qwen3 models utilize Qwen's tokenizer, which implements byte-level byte-pair encoding
(BBPE ...) with a vocabulary size of 151,669" -- while 151,936 is `vocab_size` in the shipped
configuration, the padded height of the embedding matrix (151,669 rounded up to a multiple of 128,
plus the reserved special tokens). The app displays the padded figure, which is the one that costs
parameters and HBM, and anchors it to the configuration with an `equal` pointer. The paper citation
on those three claims is **dropped**: leaving it would imply the report corroborates 151,936, and
it does not mention that number at all.

**3. Qwen3-8B: the report says 128K context, the app shows 32,768. Which is right?**
Native versus extended, and the app is right for the quantity it names. `app.mjs` calls this value
"the native context used by this preset", and the report states the native figure in its own
sentence: "All models are pre-trained on hundreds of billions of tokens with a sequence length of
32,768 tokens." The 128K in Tables 1 and 2 is the deployment length reached afterwards with YaRN
and Dual Chunk Attention, which the report introduces explicitly "to enable length extrapolation";
the shipped configuration carries a third number again, `max_position_embeddings` = 40,960, which
is the position-embedding budget and is neither of the other two. Because the report's sentence is
about "all models", one quote is safe across q38, q330 and q3235, all of which display 32,768, so
these three citations are **re-pointed** onto it. The configuration citations at the same field stay
unresolved: no key in `config.json` names the native context.

**4. `hopper-tuning` and `blackwell-tuning` were left out of quote authoring entirely.**
Two different problems were hiding under one exclusion, and they get different answers. The guides
are CUDA programming documents: a Streaming Multiprocessor section, a memory-system section, an
NVLink section, and nothing whatever about a DGX chassis. For CPU model, NIC, GPU count, board
power, peak throughput, switch count and system name they are simply the wrong document, so those
42 citations are **dropped**. For architecture, per-GPU HBM capacity, HBM bandwidth and NVLink
bandwidth and generation they *are* the right document -- the Hopper guide states "capacity up to
80 GB" and "900 GB/s bidirectional bandwidth", the Blackwell guide states "capacity up to 180 GB"
-- but each guide is cited by two SKUs with diverging values (80 GB against H200's 141 GB, 180 GB
against GB300's 288 GB), and one quote per `(source, field)` would silently back the wrong one.
Those 20 stay **unresolved** under the tool cap in finding 6.

**5. `gb300` and `b200` per-GPU HBM and NVLink GB/s: the vendor pages state only aggregates.**
Confirmed. The DGX B200 pages give "1,440 GB total GPU memory" across eight GPUs and the GB300
page gives rack totals; the per-GPU 180 and 288 the app displays appear on neither. Dividing the
aggregate by the GPU count is a derivation, and these claims are `documented` with no
`dependencies`, so the manifest does not model it as one. Left **unresolved**. The honest repair is
to restate them as `derived` claims depending on the aggregate and on `gpus`, which is a
manifest-shape change beyond this task. Note the cross-reference: the Blackwell tuning guide does
state B200's 180 GB per GPU directly, and it is finding 4 -- not the absence of evidence -- that
keeps that row unanchored.

**6. Tool cap: `QUOTES` keys on `(source, field)` and not on model.**
A source cited by several checkpoints can therefore only carry facts that are identical across all
of them. This is why per-model paper facts stayed unanchored: `q3-paper` backs q38, q330 and q3235
at once, `hopper-tuning` backs h100 and h200, `blackwell-tuning` backs b200 and gb300. 52 residue
rows sit on such a shared key. Re-keying on `(source, model, field)` would unlock roughly **24** of
them -- 13 from Tables 1 and 2 of the Qwen3 report (layers, Q/KV head counts, expert counts) and 11
from the tuning guides (architecture, NVLink generation, per-GPU HBM, NVLink bandwidth) -- and would
turn the other 28 into an honest "this source does not state this figure". It is recorded here and
deliberately **not fixed**: it is out of scope for this task.

**The rule, in one sentence: a `python_symbol` anchor is honest when the symbol's own span either
names the publisher parameter the claim transcribes -- at its declaration site or at a use site
that gives it its meaning -- or implements precisely the mechanism the claim names; a class that
merely sits nearby in the same file is not a referent.** That is the test to apply to the tenth
checkpoint without re-deriving it.

Two corollaries. `dspark_n_routed_experts` is declared in `ModelArgs` and returned by
`ModelArgs.get_moe_config`, so that method -- where the value acquires its meaning for the draft
layers -- is a referent, while `DSparkBlock`, which never reads it, is not. And **a textual hit is
not a binding**: searching `Attention` for a QK-Norm matches `q_norm`, which is a different
normalization, and that is how a false anchor survives review.

### The fence: `contains` on every standing anchor

Ruling T13c. The audit above was applied by hand, and nothing would have stopped the same bindings
being written again -- except that `select_anchor` already enforces `contains` tokens on
`python_symbol` anchors, and `verification/evidence.py` makes them mandatory for `span` and
`text_quote` while leaving them optional here. So all **69** `python_symbol` anchors on
`MODELS.dsv41.*` claims now declare the token that makes their symbol the right symbol: the
attribute or key whose presence in the span is the evidence the audit read. `ff` names
`args.moe_inter_dim`, `shared` names `args.n_shared_experts == 1`, `nopeDim` names
`self.nope_head_dim = args.head_dim - args.rope_head_dim`, `swaKvFormat` names the sentence "stays
fp8, quantized over the whole post-RoPE vector". Re-acquired against the publisher bytes: **69
resolved, 0 refused**.

This converts a review-time judgement into a resolution-time refusal. `Gate` with
`contains: ['n_activated_experts']` resolves; `Gate` with `contains: ['args.moe_inter_dim']` is
refused with "Required token not in selected code" -- so the false binding that survived three
rounds of review could not have been recorded at all. The remaining asymmetry is deliberate and
parked with a figure rather than guessed at: **5,837 `python_symbol` anchors on the other eight
checkpoints carry no `contains`**, so making the token mandatory in `select_anchor` would refuse
every one of them until each is authored. That is a decision about 5,837 anchors, not about this
model.

Every hash and span was resolved by a committed tool against the pinned bytes: the pointers by
`anchor-configs.py`, the quotes by `anchor-documents.py`, and the `python_symbol` anchors by
`python -m verification.sources acquire`, which re-fetched each publisher file it needed -- every
re-fetched digest equal to the accepted one, so no accepted byte was overwritten -- and stamped
what resolved. None was hand-written.

Only `swigluLimit` appears in the census table below, as `numeric-format-alias`: the other pointer
and quote resolutions were clean, and a clean resolution emits no residue row. The four drops
appear as `presentation-label`, and `test_every_dropped_citation_is_gone_from_the_manifest` holds
the record and the manifest together. The `python_symbol` rows appear nowhere in the census at all,
for the reason the header states.

`compress_ratios` is the one genuinely new selector shape: an INDEXED pointer. `ModelArgs` in the
publisher's `model.py` documents the field as "one entry per layer, MTP layers included: 0 =
sliding window only, r = KV compressed r-to-1", so the value at an index IS that layer's
compression ratio. In the pinned bytes the runs are 0 at layers 0-1, **2 at layers 2-19**, **1 at
layers 20-39**, and 0 at the three MTP layers: index 2 is an encoder layer holding 2, index 20 a
decoder layer holding 1. Two things follow and both are recorded rather than smoothed over. First,
`compressEncoder` is not uniform across the encoder -- layers 0 and 1 carry 0, not 2 -- so the
anchor pins one layer's published ratio, which is the quantity the claim names, not a proof that
every encoder layer shares it. Second, the pointer is emphatically NOT available to
`encoderLayers`: see the `inferred-boundary` class.

Not anchored, each for a reason and not for lack of looking:

- **`encoderLayers`**: the CONFIGURATION and CODE citations stay `anchor:null`. Ruling T13a added
  the card citation and its quote, because the publisher states the split in words; `config.json`
  still does not, and `Transformer.__init__` builds one flat `nn.ModuleList` that encodes no
  boundary. A field can be anchored in one source and honestly unanchorable in another.
- **`ngram`**: the card states "196B parameters" against the displayed 196,613,849,600. Same
  quantity, lower precision; a quote saying 196B does not state the number the claim asserts.
- **`swaKvFormat`**, by the configuration and the card: neither names a cache format. The
  publisher's code does, and the claim is anchored there instead -- see `documented-only-in-code`.
- **Absence defaults** (`kvRank`, `latent`, `linearHeads`, `linearKeyHeads`, `pleLayers`, `gate`,
  `denseLayers`): RULING (L/N). `config.json` carries `attention_bias: false` and would happily
  match a falsy displayed value, which is exactly the coincidence an earlier audit found 91 of.
- **`nopeDim`, `swaLayers`, `vision`, `ngram`, `residual`**: each follows from an expression over
  the same bytes, and `verification/ced.py` FIELD_MAP already checks that arithmetic against the
  publisher document. An anchor pins bytes, not arithmetic.

**Not censused: 75 code citations, and what was done about the 64 there were.** Neither authoring
tool enumerates `publisher_code` or `library_code` citations, so these are counted by
`CLAIM_ANCHOR` and classified nowhere. Nine of the 64 were anchored by declaring a symbol and
letting `verification.sources acquire` resolve it -- five on `EngramLayout`, two on
`hc_split_sinkhorn_kernel`, one on `fp4_act_quant`, one on `act_quant` -- each chosen because the
symbol READS the field the claim transcribes, or implements precisely the mechanism it names.
Reading the CALL SITE rather than the declaration is what settled the last of them: this record
nearly stated that nothing quantizes the sliding-window KV, on the strength of `window_kv_cache`
being declared as a plain buffer, when `_window_kv` quantizes the tensor to fp8 before writing it
in. What remains, and why each was refused rather than filled:

- **`dsv41-kernel` on `indexer`, `indexerHeads`, `indexerBudget`, `candidateBlocks`,
  `candidateBlockSize`, `candidateSource` (6 of the 8 remaining kernel citations).** `sparse_attn_kernel` takes `h` and `d` from the
  MAIN attention's tensors and `topk` as a symbolic dimension; it names no head count, no head
  width, no budget and no candidate block size, and `kernel.py` contains the string "candidate"
  nowhere. Those six values are read by `Indexer` in `model.py`, which each claim already cites
  with a resolved anchor. Binding them here would be a second anchor that resolves and says
  nothing -- the precise failure mode this branch already committed once.
- **`dsv41-kernel` on `compressEncoder`, `compressDecoder` (2).** No kernel symbol mentions a
  compression ratio; `Compressor` in `model.py` carries them and is already anchored.
- **`dsv41-engram` on `ngram` (1)** and **`dsv41-code` on `encoderLayers` (1)**: a derived product
  and a boundary the code does not encode, per the classes above. `Transformer.__init__` builds one
  flat `nn.ModuleList` over `range(args.n_layers)`; the only split it makes is the separate `mtp`
  list.
- **`nccl-api`, `nvshmem-api`, `nixl-api` on 15 network scene claims each (45).** Same reasoning as
  `scene-signature`: the claim's `expected` is a digest of our own scene contract.
- **The 20 citations the audit unanchored** are uncensused code citations too: `dsv41-code` on
  `architecture`, `generation`, `repo`, `summary`, `maxContext`, `configMax`, `qkNorm`, `swaLayers`,
  `ngram`, `denseLayers` (twice, on `Gate` and `MoE`), `routeScale`, `scoring`, `expertFF`, `ff`,
  `shared`, and `dsv41-vision` on `visionLayers`, `visionHeads`, `visionFF`, `visionPatch`. Each
  keeps its citation -- the file is the right provenance for the mechanism -- and none keeps a
  selector, because no span in it carries the value. Where another span did, the anchor moved there
  instead: six of them.

A census that enumerates code citations is still the honest next step. What is now settled is that
no new tool is needed to ANCHOR them: `acquire` resolves any declared `python_symbol`, so the only
work per citation is the reading that decides whether a symbol carries the value -- which is the
work that matters, and is how the first round of this branch came to bind `Attention` to Engram,
DSpark and the vision encoder with hashes that all resolved.


## Why each class was decided that way


### `absence-assertion` — unresolved (162)

The displayed value asserts an ABSENCE -- numeric 0, empty list, false, or a null where no figure is published. RULING (L/N) and the project's own non-negotiable ("Do not turn missing numeric evidence into zero") forbid anchoring these: a config key holding a falsy value does not document an absence, and a paper does not document one by failing to mention it. Permanently unresolved by policy, not by omission.

### `activation-alias` — re-pointed (1)

The publisher configuration says `"swish"` where the app displays `SiLU`. These are the same activation function under two names (SiLU is Swish-1), so the pointer is a true anchor and it stands. The relation is deliberately left `documents` rather than upgraded to `equal`: `equal` runs a byte comparison of the upstream value against the displayed one, and asserting that `"swish"` and `"SiLU"` are the same bytes would be false. The naming difference is a real, recorded fact about the two vocabularies, not a defect to be smoothed over.

### `architecture-fact` — unresolved (20)

Blocked by a known cap in the authoring tools, not by the source. `QUOTES` in `tools/anchor-documents.py` keys on `(source, field)` and not on model, so a source cited by several checkpoints can only carry facts identical across all of them. `q3-paper` backs q38, q330 and q3235 at once; `hopper-tuning` backs h100 and h200; `blackwell-tuning` backs b200 and gb300. Where the value diverges per model -- layer counts, hidden sizes, expert counts, per-GPU HBM -- one quote would silently back another model's different number, so no quote was authored. Unresolved, and deliberately not fixed here: re-keying `QUOTES` on `(source, model, field)` is out of this task's scope. Estimated unlock if it were re-keyed: about **24 of these 52 rows**. Tables 1 and 2 of the Qwen3 report give layers, Q/KV head counts and expert counts per model (13 rows), and the tuning guides name their architecture, NVLink generation, per-GPU HBM capacity and NVLink bandwidth per architecture (11 rows). The other 28 would then read honestly as "this source does not state this figure" -- the Qwen3 report never gives hidden size, FFN width, per-model parameter counts or expert FFN width, and the tuning guides state a "up to 3 TB/s" architectural ceiling rather than the 3.35 and 4.8 TB/s the H100 and H200 datasheets carry.

### `authored-prose` — unresolved (16)

`MODELS.*.summary` is prose we wrote; `MODELS.*.repo` is the identifier of the source itself rather than a fact any source asserts. Reclassifying them would need `PRESENTATION_SUFFIXES` widened, and that is a policy-root change explicitly out of scope here. Left unresolved so the decision stays visible rather than being smuggled through the whitelist.

### `card-published-figure` — unresolved (5)

A figure the publisher states in the MODEL CARD and `config.json` does not carry at all: backbone parameters, activated parameters per phase, bytes of KV per token, the main KV format. The card citation on each of these claims now carries a `text_quote` anchor resolved against the pinned README bytes; what stays unanchored is the CONFIGURATION citation, which is blanket provenance for the checkpoint rather than a span stating this figure. Kept rather than dropped -- the config is the document the rest of the claim set is anchored to, and citing it is not false -- and unresolved, because no key in it names these quantities.

### `chassis-fact` — dropped (42)

The CUDA tuning guides are programming guides for an architecture. They contain a Streaming Multiprocessor section, a memory-system section and an NVLink section, and they state nothing about a DGX chassis: no CPU model, no NIC, no GPU count, no board power, no peak throughput, no system name. Citing them for those fields is false provenance, so the citation is dropped. Every affected claim still cites the product page and the system guide, both `vendor_document`, so no required role is lost.

### `code-digest` — dropped (15)

A sha256 of `src/core.mjs` or of `parameterLedger` is a fingerprint of code we wrote. The Kimi K3 paper does not document it, and these claims depend on all nine checkpoints, so citing one model's paper is arbitrary as well as false. Dropped; the publisher/framework code citations on the same claims are untouched.

### `config-derived-value` — unresolved (4)

The value follows from an EXPRESSION over these same bytes and no single span states the result: `nopeDim` is `head_dim - qk_rope_head_dim`, `swaLayers` counts the zero entries of `compress_ratios`, `vision` is whether `vision_config` is present, `ngram` is `sum(engram_num_embeddings) * engram_head_dim`. `verification/ced.py` FIELD_MAP carries each expression and the CED verifier checks the arithmetic against the publisher bytes independently. That is a different thing from an evidence anchor: `select_anchor` pins bytes, so a pointer here would clear `CLAIM_ANCHOR` on our own arithmetic. Unresolved on purpose.

### `contract-semantics` — unresolved (29)

The claim's last segment is a SKU, fabric or library name (`H100-SXM`, `RoCEv2-lossless`), not a field name, and `expected` is null -- there is no value a quote could corroborate. The authoring tools key on `(source, field)`, so no key can address these. Left unresolved; contract records need per-contract quote authoring, which the current tool shape cannot express.

### `documented-only-in-code` — unresolved (2)

Neither of these two DOCUMENTARY sources names a format for the sliding-window KV: `config.json` declares no cache format at all, and the model card describes SWA Bounded Replay and stops there. The technical report does state it and cannot help, because it is a PDF and both `verification/sources.py` and `verification/evidence.py` decode strictly as UTF-8 before any other check -- the report is deliberately absent from the catalog rather than present and unresolvable.
